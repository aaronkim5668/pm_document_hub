## 1. 기술적 리스크

### R-T1. pg_bigm 설치 실패 또는 누락

| 항목 | 내용 |
|---|---|
| **리스크** | 운영 환경에 pg_bigm 확장이 없으면 한국어 검색이 동작하지 않음 |
| **발생 확률** | 중간 (표준 PostgreSQL 배포에는 미포함) |
| **영향** | 검색이 핵심 진입점인데 동작 불가 → MVP 목표 달성 불가 |
| **완화** | ① Docker Compose로 pg_bigm 포함 이미지 제공 (`pgbigm/pg_bigm:15-2.0`). ② 미설치 시 `ILIKE '%keyword%'` fallback 자동 전환. ③ 설치 스크립트 `setup.sh` 제공. ④ `검색 fallback 모드` 배너 표시 |
| **수용 기준** | fallback 모드에서도 검색 동작. pg_bigm 활성화 후 성능 격차 < 2x |

### R-T2. 텍스트 추출 품질 (PDF/DOCX)

| 항목 | 내용 |
|---|---|
| **리스크** | 스캔 PDF, 이미지 기반 PDF, 복잡한 레이아웃 DOCX에서 텍스트 추출 실패 또는 의미 없는 텍스트 추출 |
| **발생 확률** | 높음 (게임 기획서는 표/이미지/다이어그램 혼합이 많음) |
| **영향** | 추출 성공해도 검색·변경사항 추출이 무의미해짐 |
| **완화** | ① parse_warning 필드에 "텍스트 비율 낮음" 경고 저장. ② 추출 텍스트 길이 < 200자면 사용자에게 수동 보완 안내. ③ parse_status = partial 상태 추가 검토. ④ Raw Upload 후 AI Import로 전환 유도. ⑤ **[A2] PPTX 추출:** officeparser 사용 — unzipper+xml2js 대비 한국어 인코딩 안정적. 단, 복잡한 레이아웃·이미지 내 텍스트는 partial 처리 가능 (mvp_spec F11 기준 부분 지원 명시). |
| **수용 기준** | 추출 실패 시 사용자가 상태를 인지하고 AI Import로 fallback 가능 |

### R-T3. 한국어 텍스트 변경사항 추출 정확도

| 항목 | 내용 |
|---|---|
| **리스크** | 버전 간 diff 추출이 한국어 조사 변화, 동의어, 수치 표기 혼용(1,000 vs 1000 vs 1K)으로 인한 false positive 다발 |
| **발생 확률** | 높음 |
| **영향** | 변경사항 후보가 노이즈로 가득 차면 패치노트 생성 품질 저하 |
| **완화** | ① 수치 정규화: 쉼표 제거, "1K→1000" 치환 후 비교. ② 변경 유형을 number_change / text_change / added / removed로 분류. ③ MVP에서 변경사항 후보는 "후보" 상태로만 노출하고 사용자가 직접 선택 (자동 승인 금지). |
| **수용 기준** | 사용자가 후보 목록에서 실제 변경사항을 80% 이상 식별 가능 |

### R-T4. AI API 비용 초과

| 항목 | 내용 |
|---|---|
| **리스크** | 명시적 사용자 요청 없이 AI 호출이 발생하거나 월 예산 초과 |
| **발생 확률** | 낮음 (Non-Negotiable로 설계에서 차단) |
| **영향** | 예상치 못한 비용 발생 |
| **완화** | ① `budget-guard.ts` 미들웨어: 매 AI 호출 전 `monthly_budget_usd` 잔액 확인. ② 예산 0 = DB 레벨에서 완전 차단 (UI bypass 불가). ③ 80% 도달 시 UI 경고 배너. ④ AI 호출 시마다 `AIUsageLog` 기록. ⑤ **[B2] Decimal 비교:** `monthly_budget_usd`는 Prisma `Decimal` 타입 — `=== 0` 직접 비교 시 항상 `false` (budget guard 우회). 반드시 `.toNumber() === 0` 또는 `Prisma.Decimal.equals()` 사용. |
| **수용 기준** | 예산 0 설정 후 어떤 경로로도 AI API 호출이 발생하지 않음 (E2E 테스트로 검증) |

### R-T6. Next.js body size 제한 (파일 업로드 4MB → 20MB)

| 항목 | 내용 |
|---|---|
| **리스크** | Next.js App Router 기본 body size limit 4MB. 20MB 파일 업로드 시 `413 Payload Too Large` 오류 |
| **발생 확률** | 높음 (미설정 시 Raw Upload 기능 즉시 실패) |
| **영향** | Phase 2 Raw Upload 기능 전체 동작 불가 |
| **완화** | `next.config.js`에 `experimental: { serverActions: { bodySizeLimit: '20mb' } }` 설정. 또는 `app/api/upload/route.ts`에서 `request.formData()` 스트리밍 처리 (기본 body parser 우회). 환경 설정 체크리스트에 포함 (Section 2). |
| **수용 기준** | 20MB 파일 업로드 성공, 20MB+1B 즉시 거부 (upload_status=failed, 에러 메시지 표시) |

### R-T5. JSON Import Schema 설계 경직성

| 항목 | 내용 |
|---|---|
| **리스크** | GPT 정제본 JSON 포맷이 실제 사용 패턴과 맞지 않으면 Import 실패가 반복됨 |
| **발생 확률** | 중간 (초기 스키마는 가정 기반) |
| **영향** | AI Import 핵심 기능이 사용되지 않음 |
| **완화** | ① JSON Schema를 최소 필수 필드 3개 + 선택 필드 구조로 설계 (엄격한 검증 지양). ② 스키마 버전(`$schema_version`) 필드로 향후 변경 가능. ③ 검증 실패 시 어느 필드가 문제인지 필드 단위 오류 메시지 표시. |
| **수용 기준** | 첫 실제 GPT 정제본으로 Import 성공률 80% 이상 |

## 2. 제품/UX 리스크

### R-P1. MVP 범위 크리프

| 항목 | 내용 |
|---|---|
| **리스크** | 4주 일정에 19개 기능 포함. 주간 우선순위 재조정 없으면 Phase 3 (패치노트)가 미완성으로 끝날 위험 |
| **발생 확률** | 높음 |
| **영향** | Non-Negotiable #8 위반 — 패치노트 생성이 MVP 포함이어야 함 |
| **완화** | ① Phase 1 > Phase 2 > Phase 3 순으로 단계 잠금. 이전 Phase 완료 전 다음 Phase 착수 금지. ② 주간 마일스톤 기준으로 진행 여부 판단. ③ Phase 2 Raw Upload가 지연되면 AI Import 단일 경로 MVP로 축소 후 Phase 3 우선 완료. |
| **수용 기준** | 4주 종료 시 패치노트 초안 1건 생성 E2E 동작 |

---

### R-P2. 버전 충돌 UX — 사용자가 Review Queue를 무시

| 항목 | 내용 |
|---|---|
| **리스크** | 충돌 항목이 Review Queue에 쌓이는데 사용자가 확인하지 않으면 최신 문서가 반영 안 된 채 방치됨 |
| **발생 확률** | 중간 |
| **영향** | "이 도구에 넣으면 최신 문서가 관리된다"는 핵심 가치 훼손 |
| **완화** | ① 메인 페이지에 Review Queue 대기 건수 배너 표시. ② 검색 결과에서 "버전 충돌 있음" 배지 표시. ③ MVP에서 복잡한 자동 해결 로직 없이 단순 승인/거부 UI만 제공. |
| **수용 기준** | 사용자가 Review Queue 존재를 인지하고 7일 내 처리 |

---

### R-P3. Raw Upload 텍스트 추출 결과 불신

| 항목 | 내용 |
|---|---|
| **리스크** | 추출된 텍스트가 원본 레이아웃과 달라 사용자가 결과를 신뢰하지 않음 |
| **발생 확률** | 중간 |
| **영향** | Raw Upload 기능 사용 포기 → AI Import만 사용 → 사용자 부담 증가 |
| **완화** | ① 추출 텍스트와 원본 파일 다운로드를 나란히 표시. ② "원본 파일은 항상 보존됨" 명시. ③ 추출 결과가 불만족스러우면 AI Import로 재등록 유도 (두 경로 병행 지원이 설계 원칙). |
| **수용 기준** | 사용자가 추출 결과에 불만족해도 원본 파일 다운로드로 복구 가능 |

### R-P4. 변경사항 후보 누락 (False Negative)

| 항목 | 내용 |
|---|---|
| **리스크** | diff 알고리즘이 실제 중요한 변경사항을 감지하지 못함 |
| **발생 확률** | 중간 |
| **영향** | 패치노트에 빠진 항목 → 릴리즈 오류 |
| **완화** | ① 변경사항 후보는 "패치노트 생성의 보조 도구"로 포지셔닝. 사용자 최종 검수 원칙 유지. ② 변경사항 후보 외에도 문서 상세에서 직접 항목 추가 가능. ③ "이 버전에 감지된 변경사항 없음" 명시적 표시. |
| **수용 기준** | 패치노트 생성 시 직접 추가 항목을 수동 입력 가능 |

## 3. 인프라/운영 리스크

### R-S1. 인증 없는 LAN 노출 (v1 설계 결정)

| 항목 | 내용 |
|---|---|
| **리스크** | 툴이 0.0.0.0:8787로 바인딩되어 오피스 내부망 전체에서 접근 가능. v1에 인증 없음. |
| **발생 확률** | 낮음 (오피스 LAN은 내부 접근 제어됨. 단, 인터넷 직접 노출 시 즉시 높음.) |
| **영향** | 오피스 LAN 내 모든 사용자가 게임 기획 문서 전체에 무제한 접근 가능. 외부 노출 시 기획 정보 유출 위험. |
| **완화** | ① 툴을 인터넷에 절대 노출하지 않음 (포트포워딩, 클라우드 배포 금지). ② 오피스 방화벽에서 8787 포트를 외부 차단. ③ v1.5 Backlog: 기본 인증(로그인 + 세션) 추가. ④ 외부 배포 또는 팀 외부 공유가 필요해지면 반드시 인증 먼저 구현. ⑤ **[NET1] Windows 머신 실행 시** Windows Defender 방화벽 인바운드 규칙에 포트 8787 TCP 허용 추가 필요 (팀원 LAN 접속을 위해 필수 — 미설정 시 PM 로컬에서만 접속 가능). |
| **수용 기준** | 툴 URL이 오피스 외부에서 접속 불가 확인. v1.5 인증 구현 전 외부 배포 금지. |
| **v1 결정 근거** | 팀 내 공유 툴로 사용하기 위해 127.0.0.1 대신 0.0.0.0으로 설계. Port 3000(방화벽 차단), 8080(충돌) 대신 8787 사용. 인증은 PM 단독 → 팀 확장 시 1.5차에서 추가. |

## 4. 주요 트레이드오프 결정 기록

### TO-01. Next.js API Routes vs 독립 백엔드 서버

| 항목 | 내용 |
|---|---|
| **선택** | Next.js API Routes (서버리스) |
| **이유** | 내부 툴 단일 사용자, 별도 서버 관리 오버헤드 불필요. Prisma 직접 연결 가능. |
| **포기한 것** | 백그라운드 작업 처리의 한계 (파일 추출 등 오래 걸리는 작업) |
| **완화** | 파일 추출은 동기 처리로 충분 (내부 툴, 동시 요청 없음). 추후 Queue가 필요하면 분리. |

---

### TO-02. Supabase Storage vs 로컬 파일시스템

| 항목 | 내용 |
|---|---|
| **선택** | 로컬 파일시스템 (MVP) |
| **이유** | 외부 의존성 제거, 즉시 개발 시작 가능, 내부 툴에서 클라우드 불필요 |
| **포기한 것** | 멀티 디바이스 접근, 자동 백업 |
| **완화** | `STORAGE_TYPE` 추상화로 v2 전환 비용 낮춤 |

---

### TO-03. pg_bigm vs Elasticsearch

| 항목 | 내용 |
|---|---|
| **선택** | pg_bigm (PostgreSQL 확장) |
| **이유** | 별도 서비스 불필요. PostgreSQL 단일 DB로 관리. 100건 이하에서 500ms 목표 달성 충분. |
| **포기한 것** | Elasticsearch의 고급 랭킹, 동의어 처리, 필드 가중치 |
| **완화** | 문서 수 1,000건 초과 또는 검색 요건 복잡해질 경우 v2에서 pg_vector 또는 Elasticsearch 검토 |

### TO-04. 변경사항 추출: 규칙 기반 vs LLM

| 항목 | 내용 |
|---|---|
| **선택** | 규칙 기반 diff (MVP) |
| **이유** | LLM 의존 없이 결정론적 결과. API 비용 0. 빠른 구현. |
| **포기한 것** | 의미 기반 변경사항 감지 (수치 표기 혼용, 동의어, 컨텍스트 변화) |
| **완화** | 수치 정규화 전처리. 후보는 항상 사용자 확인 요구. LLM 기반은 v2 고도화. |

### TO-06. 인증 없는 LAN 공유 vs 인증 포함

| 항목 | 내용 |
|---|---|
| **선택** | v1: 인증 없이 LAN 공유 |
| **이유** | 오피스 내부망은 신뢰된 환경. 인증 구현 비용(로그인, 세션, 권한 테이블)이 MVP 일정에 부담. 팀 내 즉시 공유가 우선. |
| **포기한 것** | 접속자 식별, 문서 접근 이력, 권한 기반 편집 제어 |
